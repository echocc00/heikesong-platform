# 需求溯源表 · AI 商业黑客松赛事平台

> **用途**：平台每一个功能需求，都必须能回答三个问题——**它从哪来**（源文档 + 定位）、**它是什么**（可判定的行为）、**它凭什么这么定**（机制归因）。
> **纪律**：需求不是"我觉得该有"，而是"某份文档写了，且我们决定落地"。
> **状态口径**：
> - `已定` = 任务书/组委会已定规则，实现必须严格符合
> - `机制件` = 我方机制件（S7/S10/SABC）写明的设计，**待组委会确认**
> - `我方假设` = 无外部依据，我方拍板，**首届时须回测**
> - `待验证` = 依据本身未验证，实现时须留出口以便调整

**分母声明**：本次分母 = 平台需求全集｜来源 = 任务书 2.0（筹备赛发起说明书）+ 组内 3 份机制件（S7 评分机制 / S10 积分段位 / SABC 报名画像）+ 项目自身复盘（周报、一页纸、evidence-chain Skill）｜独立源数 = 6 份一手文档（同一作者体系，非独立互证）

**⚠️ 溯源表的性质**：这 6 份文档同属一个团队的产出，**不构成多方独立互证**。它们是"我们自己的规则"，不是"行业已验证的规则"。凡本表标 `我方假设` 的条目，实现时必须做成**配置项而非硬编码**，以便首届后按实测调整。

**⭐ 机制归因（这是整个平台最需要被代码强制的一组规则）**：
- R-JDG-02 的理由是「A 评委一贯给 85、B 评委一贯给 70，差异不代表项目更差，只代表 B 更严格。直接加权相加，榜单实际是"谁遇到了宽松的评委"」——**这是最隐蔽的评审失效，肉眼看不出来**。
- R-JDG-06/R-JDG-07 的理由是「企业既是出题方、又是评审方、还可能是甲方，天然有动机打高分」。R3 存在的原因：**若企业席扩到 8 人而评委席只有 5 人，"企业确认 25%"实际就是"企业说了算"**。R3 让这条规则在人数变动时不会失控。
- R-JDG-13 的理由是「一旦自评可以加分，它就变成了纯粹的博弈项。让它只触发"解释"和"提问"，它才真正对治黑箱」。

**⭐ 机制归因（分轨的三条硬约束，全部要在代码层强制）**：
1. **R-PTS-08 的实现方式决定了整个体系成不成立**。S10 §8 第三条风险原文：「行为分被当成主评分……⭐ **算法层面强制分离**，不依赖人的自觉」「**分轨必须是算法层面的，不是纪律层面的**」。→ 总分函数签名里根本不接收行为分。
2. **R-RNK-01 + R-PTS-12 的实现方式**：A 榜和 B 榜共享「企业签字」数据源，但走两条不同的表和两条不同的计算路径，任何一条都不能读另一条的分数字段。
3. **R-JDG 与 R-PTS 的"企业签字"是两个不同实体**：S7 §5 修正②原文——`w_E` 是「企业觉得这个做得好不好」（主观评价，需双签制衡），B 榜签字是「这件事到底发生了没有」（客观事实，无需平衡）。→ 数据模型必须是两个表，不是同一张表加两个字段。

**⭐ 一条贯穿全表的设计结论**：
> **60 条机制件级需求全部来自我们自己尚未被组委会确认的设计。若把它们硬编码进业务逻辑，一旦组委会改一次数值，就要改代码、重新部署、重新验证。**
> → 所以核心规则（权重表、段位表、行为分明细、阈值、可见性策略）全部走**声明式配置**，规则引擎是纯函数，输入配置 + 输入数据 → 输出结果 + 输出计算快照。**换一次规则 = 改一份 JSON，不改一行代码。**

**⭐ 第二条结论（来自 §规则冲突登记表）**：
> S7 / S10 内部已查出 **6 条自相矛盾或跨文件冲突**（`docs/rule-decisions.md`），其中 C-01（初赛 `w_E` 10% vs 20%）若硬编码，**初赛榜单会整体错位且不报错**——名次看起来仍然合理，不会有人发现。
